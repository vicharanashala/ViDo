Check git remote -v before preparing a branch. Read AGENTS.md and its required project guides before making changes. Check Node, npm, Java, and Firebase CLI availability. 1. Coordinate the change

Search issues and open pull requests for related work. Report a bug in an issue. For a feature, start a thread in the Ideas category of GitHub Discussions. Share a UI redesign or mockup in General. Agree on scope with the maintainers before implementation.

What should I include in the issue or discussion?

For a bug, identify the route, browser and OS. Give the shortest steps that reproduce it and describe the expected and actual results. For a proposal, explain who needs the change, which workflow it improves, and how the design fits ViDo. A small mockup can help settle the interaction.

2. Fork and create a branch

Fork ViDo into your GitHub account. Replace YOUR-USERNAME in the command below. Your clone calls your fork origin. Add the project repository as upstream.

git clone https://github.com/YOUR-USERNAME/ViDo.git
cd ViDo
git remote add upstream https://github.com/vicharanashala/ViDo.git
git switch main
git pull --ff-only upstream main
git switch -c fix/123-task-date-label

Replace 123 with the actual bug issue number. Choose a branch name that describes your change, such as feature/calendar-filters for a feature. Follow local setup to run the parts of the app you need.

3. Develop and verify

Keep the change focused on the linked issue or discussion. Keep new behavior in its owning feature. Add colocated unit or integration coverage for each new component or logic helper, and preserve existing assertions.

Run the required checks and record their results in your PR.

Planning a substantial change with OpenSpec

Prepare a change under openspec/changes/ with a proposal, requirements, design, and task list. Review the scope and acceptance criteria before coding. Update the tasks as you implement and verify them, then archive the change after review. See the OpenSpec walkthrough.

4. Submit the pull request

These commands are for the contributor publishing to their own fork. An agent needs your explicit instruction to push. Review your diff, stage the intended files, and write a conventional commit message. For example, a fix on the branch above could use these commands.

git diff
git add -p
git diff --cached
git commit -m "fix: clarify task date label"
git push -u origin HEAD

Stage any new files by name with git add. On GitHub, open Compare & pull request. Select vicharanashala/ViDo:main as the base and your fork’s topic branch as the head. Describe the change and how you verified it.

What should reviewers see in the PR?
  • A conventional title and a short description of the user-visible result.
  • A linked issue, such as Fixes #123 using the actual issue number, or the approved discussion for a feature or redesign.
  • For UI changes, the approved Discussion link, affected route or endpoint, and before-and-after screenshots or a recording.
  • The verification commands you ran and their results.

Respond to review comments and push revisions to the same branch. GitHub updates the existing PR with those commits. Read the project contribution guidelines.

Before you request review

Check the fork, base branch, and file list in GitHub’s comparison. An agent may inherit a checkout where origin points to the main project. Run git remote -v before pushing. Give the agent explicit permission before it publishes a branch or PR.

Prompt for your agent

Compare this branch with the current upstream main. Summarize each user-visible change, list the files that implement it, and give me the checks you ran with their results. Identify any untracked work that belongs in the PR. Draft the PR description for my review.
