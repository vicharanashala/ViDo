Design principles

The product brief sets six working principles for decisions about language, layout, and task behavior. Read the concept brief.

Universal language

Avoid terminology that assumes office work. The same interaction should make sense for groceries, schoolwork, maintenance, or client delivery.

Clarity before density

Organize information through sections, hierarchy, and progressive disclosure instead of displaying every property at once.

Motivation without guilt

Help users act on overdue work without confronting them with a discouraging wall of red tasks or punitive language.

Professional and minimal

Use restrained visuals, predictable interactions, strong spacing, and clear typography rather than decoration or gamification.

Simple states

Tasks begin with only Active and Completed. Today, Upcoming, and Needs Attention are calculated views, not extra statuses to maintain.

Build capability gradually

Private tasks establish the core. Shared tasks, richer organization, reminders, dark mode, and AI arrive only when their foundations are clear.

Implementation milestones

The original roadmap runs from discovery through Phase 1 release review. Each milestone ends with a review before the next begins. Expand a milestone for its planned scope and the evidence in the current repository.

M0 · Product Discovery

Original scope. The concept records the audiences, first task journey, and scope agreed during discovery.

Current implementation. The living brief and original roadmap are available in the repository.

M1 · Static Visual Foundation

Original scope. Establish the design system, public landing page, and sample dashboard before connecting services.

Current implementation. The visual foundation change is archived. The landing page, style lab, and interactive preview are available.

M2 · Google Authentication

Original scope. The roadmap proposed Google OAuth through Supabase, with private routes, session handling, profile display, and sign-out.

Current implementation. The archived authentication change delivered Google sign-in through Firebase. The current authentication spec describes session and sign-out behavior.

M3 · Private Task Storage

Original scope. Provide durable, owner-scoped private tasks with PostgreSQL, row-level security, typed access, and isolation checks.

Current implementation. Personal tasks currently use browser storage keyed by user ID. Firestore persists signed-in calendar events and planning targets. Durable private-task storage remains open.

M4 · Core Task Lifecycle

Original scope. Create, inspect, edit, complete, undo, and reopen tasks, including consistent deadlines and completion timing.

Current implementation. Creation, details, completion, and reopening are implemented. Editing an existing deadline or priority is tracked separately.

M5 · Dashboard and Derived Views

Original scope. Derive Home, Today, Upcoming, Needs Attention, Completed, and Archived from task data. Review section limits, ordering, and date boundaries.

Current implementation. The workspace provides the derived views. The historical Home targets were five Today items and three each for Needs Attention, Upcoming, and Recently Completed.

M6 · Search and Filters

Original scope. Combine keyword search with priority, deadline, and state filters. Make active filters visible and support clearing them together.

Current implementation. The Tasks view includes search and filter controls. The detailed roadmap lists the original acceptance checks.

M7 · Archive, Delete, and Reliability

Original scope. Support archiving, restoring, and confirmed permanent deletion. Exercise interrupted requests, retries, and expired sessions.

Current implementation. The Archived view exists. End-to-end restore, deletion, and failure recovery still require verification against the roadmap.

M8 · Phase 1 Polish and Release Readiness

Original scope. Review mobile layout, keyboard and modal behavior, contrast, reduced motion, documentation, and critical task tests before release.

Current implementation. Automated coverage and setup guides are present. The original release criteria also call for privacy checks and a review of the complete user journey.

Workspace architecture

The landing page leads into two versions of the same React shell. The route determines the identity, the starting data, and where updates go.

Trace a personal task completion

In the detail modal, Mark as Complete calls the toggle handler in WorkspaceLayout. The handler sets the completion time and appends a checkpoint. The derived views then pick up the new state. Reopening the task clears its completion time.

Trace a shared task update

A team lead assigns a task within a milestone. The assignee updates progress and can add a note. Team components call the methods in teamRepository.ts. With NestJS selected, the API validates the user’s Firebase token and its services read or write team records through Prisma. The events module provides a Server-Sent Events stream for updates.

Where intelligent planning fits

Imagine adding a low-priority errand on an already full Tuesday. Calendar commitments describe the available time, task deadlines describe urgency, and checkpoints provide a history of how work progressed. The proposed planner would use those signals to suggest Thursday, explain why, and let the user accept or keep Tuesday. This is the product direction. The existing date filters and analytics are deterministic calculations.

Directory explorer

Follow the placement rules in FOLDER_STRUCTURE.md. Open a folder below for its rules and examples.

src/components/ui/ · Shared primitives

Keep components such as Button, Card, and Badge independent of domain models such as Task and User. Export shared primitives through index.ts and colocate their tests.

src/features/ · Product features

Keep screens and interactions in their owning slice: landing, auth, workspace, teams, or style-lab. Workspace subroute views belong in workspace/views/.

src/data/ · Models, fixtures, and calculations

Keep filters and calculations pure. Anchor sample task dates to Tuesday, 17 November 2026. Examples include sampleTasks.ts and taskFilters.ts.

src/lib/ · Planning data access

Keep Firebase initialization and Firestore reads and writes here. Calendar events use calendarStore.ts and planning targets use settingsStore.ts.

server/ · Backend service

Place NestJS controllers, services, and DTOs in their feature modules under server/src/. Keep the relational schema in server/prisma/. The events module delivers server-sent updates.

Technology stack

Interface and routing

  • React 19
  • React Router

Feature slices provide routed screens. UI primitives stay independent of task and user types.

Build and styling

  • Vite
  • TypeScript
  • Tailwind CSS v4

Vite serves the app and proxies local API requests. TypeScript checks component and data contracts. Semantic CSS variables in src/index.css define the product palette.

Identity and planning

  • Firebase Auth and Firestore

Auth identifies the workspace user. Firestore stores planning events and targets. The local emulator configuration is in firebase.json.

Team API and storage

  • NestJS 11
  • Prisma 6
  • SQLite

The local team API owns members, invitations, milestones, tasks, and checkpoints. Inspect server/prisma/schema.prisma for relationships and server/src/ for service behavior.

Testing

  • Vitest
  • Testing Library

Tests exercise pure calculations and rendered workflows with Happy DOM. Start with the colocated test for the feature you are changing.

Documentation

  • HTML
  • CSS
  • JavaScript

The wiki runs directly from docs/. The two guides share guide.css. The weekday sample in the user guide uses guide.js.

Local setup

Run commands from the repository root. Keep the frontend terminal open while you work. The preview and documentation can be explored with Vite alone.

First-time setup and app walkthrough →

Frontend and documentation

npm ci
npm run dev

Open the address Vite prints. Try /preview, /style-lab, or /docs/user.html.

Sign-in and planning data

Install the Firebase CLI and a compatible Java runtime. If the dev server has already started the emulators, use those processes. For manual startup, run the following before starting Vite.

npm run emu

The local project is demo-vido. Auth listens on 9099, Firestore on 8080, and the emulator UI on 4000.

Team API

For a fresh checkout, create the server environment file from its example. Keep any existing local configuration. Set VITE_BACKEND_TYPE=nestjs in the root .env.local. Stop the standalone Vite process before starting both services.

cp -n server/.env.example server/.env
npm ci --prefix server
npm --prefix server run prisma:generate
npm --prefix server run prisma:push
npm run dev:all

Prisma uses the configured SQLite file. Vite forwards local API requests to port 3001.

Which team adapter is active?

getTeamRepository() selects NestJS first when VITE_BACKEND_TYPE=nestjs or an API URL is supplied. Otherwise, a configured Supabase URL and anon key select Supabase. With neither configured, the factory uses the mock repository. Restart Vite after changing environment settings.

Testing and required checks

Check local sign-in

Run npm run dev to start Vite. With Java and the Firebase CLI available, Vite checks for the local emulators and attempts to start missing services. Auth listens on port 9099. Use a mock account in the sign-in popup. See local setup for manual startup.

Before submitting a change

From the repository root, run all three checks and confirm each exits successfully.

npm run typecheck
npm test
npm run build

For changes involving the backend service, also compile the NestJS server.

npm run build:server

1. Coordinate the change

Search issues and open pull requests for related work. Report a bug in an issue. For a feature or UI redesign, start a thread in the Ideas or UI/UX category of GitHub Discussions. Agree on scope with the maintainers before implementation.

What should I include in the issue or discussion?

For a bug, identify the route, browser and OS. Give the shortest steps that reproduce it and describe the expected and actual results. For a proposal, explain who needs the change, which workflow it improves, and how the design fits ViDo. A small mockup can help settle the interaction.

2. Fork and create a branch

Fork ViDo into your GitHub account. Replace YOUR-USERNAME in the command below. Your clone calls your fork origin. Add the project repository as upstream.

git clone https://github.com/YOUR-USERNAME/ViDo.git
cd ViDo
git remote add upstream https://github.com/vicharanashala/ViDo.git
git switch main
git pull --ff-only upstream main
git switch -c fix/task-date-label

Choose a branch name that describes your change, such as feature/calendar-filters for a feature. Follow local setup to run the parts of the app you need.

3. Develop and verify

Keep the change focused on the linked issue or discussion. Put new behavior in its owning feature and add or update colocated tests.

Run the required checks and record their results in your PR.

Planning a substantial change with OpenSpec

Prepare a change under openspec/changes/ with a proposal, requirements, design, and task list. Review the scope and acceptance criteria before coding. Update the tasks as you implement and verify them, then archive the change after review.

4. Submit the pull request

Review your diff, stage the intended files, and write a conventional commit message. For example, a fix on the branch above could use these commands.

git diff
git add -p
git diff --cached
git commit -m "fix: clarify task date label"
git push -u origin HEAD

Stage any new files by name with git add. On GitHub, open Compare & pull request. Select vicharanashala/ViDo:main as the base and your fork’s topic branch as the head. Describe the change and how you verified it.

What should reviewers see in the PR?
  • A conventional title and a short description of the user-visible result.
  • A linked issue, such as Fixes #123 using the actual issue number, or the approved discussion for a feature or redesign.
  • For UI changes, the affected route and before-and-after screenshots or a recording.
  • The verification commands you ran and their results.

Respond to review comments and push revisions to the same branch. GitHub updates the existing PR with those commits. Read the project contribution guidelines.
